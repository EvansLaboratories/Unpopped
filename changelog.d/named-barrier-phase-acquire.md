Oracle: a named barrier (`bar.sync` / `bar.arrive`) no longer orders a waiter after what a thread did in a LATER phase. The oracle runs the threads of a block one after another and a woken waiter took its acquire when it next ran, by which time a thread that had already run on into the next phase had left a release on the same barrier key; the waiter absorbed that release too, so an unordered read and write between two threads (a Hillis-Steele scan with the sync between a step's read and write removed, found by the conformance lane in #457) ran to completion with wrong values and no `DataRace`. Releases are now left on the key of the phase they arrive in and a waiter acquires only the phase it waited in (the records of phase `p - 2` are dropped when phase `p` opens). Verified: `tests/kernel_named_barrier_race.rs` (a warp-wide neighbour add; the synced kernel runs, the kernel without the mid sync is a `DataRace`; without this change the second one returns `Ok` with wrong values), the #457 Hillis-Steele mutant `NoSecondSync` now traps, its unmutated scan still passes, and the 208 existing test binaries of `cargo test -p unpopped` pass.
