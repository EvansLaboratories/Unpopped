## 1. The problem

`Stmt::Mma` (`crates/unpopped/src/kernel.rs`, "A warp-level matrix multiply-accumulate (ROADMAP U7 S2)") is a **per-lane** statement: every lane of the atom's scope supplies `Private` fragments `a`, `b`, `c` and receives `d`, and the atom (`MmaAtom`, `crates/unpopped/src/mma.rs`) carries the **data layouts** that say which element of the logical matrix each lane's fragment slot holds. That is the shape of PTX `mma.sync`, whose fragment layout NVIDIA fixes.

Metal does not fix one. **MSL 4.1, section 2.4 "SIMD-group Matrix Data Types", page 38 of 383, read 2026-11-25:** "Operations on SIMD-group matrices are executed cooperatively by threads in the SIMD-group. Therefore, all operations must be executed only under uniform control-flow within the SIMD-group or the behavior is undefined." and **"The mapping of matrix elements to threads in the SIMD-group is unspecified."** The types are `simdgroup_half8x8`, `simdgroup_bfloat8x8` (Metal 3.1 and later) and `simdgroup_float8x8` ("where T is half, bfloat ... or float and Cols and Rows are 8"). **Section 6.8 "SIMD-Group Matrix Functions", pages 212-213 (Tables 6.9 and 6.10), read 2026-11-25:** `simdgroup_load(thread simdgroup_matrix<T,Cols,Rows>& d, const threadgroup T *src | const device T *src, ulong elements_per_row = Cols, ulong2 matrix_origin = 0, bool transpose_matrix = false)` ("The elements_per_row parameter indicates the number of elements in the source memory layout"), the matching `simdgroup_store(thread simdgroup_matrix<..> a, threadgroup T *dst | device T *dst, elements_per_row = Cols, matrix_origin = 0, transpose_matrix = false)`, `simdgroup_multiply_accumulate(d, a, b, c)` "Returns d = a * b + c" over `simdgroup_matrix<T,Cols,Rows>& d`, `<T,K,Rows>& a`, `<T,Cols,K>& b`, `<T,Cols,Rows>& c`, `simdgroup_multiply(d, a, b)` "Returns d = a * b", the operator `*`, and the initialisers `simdgroup_matrix<T,Cols,Rows>(T dval)` ("Creates a diagonal matrix with the given value") and `make_filled_simdgroup_matrix(T value)`. Apple's own section 6.8 opens: **"Instead of using simdgroup matrix multiplication, consider using Tensors (section 2.22) and Metal Performance Primitives (section 7). Together, they provide a performant and portable library supporting more general matrix and tensor operations across a wider variety of dimensions and extents."** (Apple itself points past the opaque tile to a tensor type: evidence for Q1 option A; MSL sections 2.22 and 7 were not read.) So there is no honest Apple fragment layout to put in an `MmaAtom`, and an `Mma` flag would assert a layout nobody documents.

Mojo rows 71 and 72 (`docs/ir-union-evidence/rescore-2026-11-25/mojo.md`) name the Apple 8x8 simdgroup MMA atom ("shipped AMD/Apple MMA atoms and emitters").

## 2. The statements

Four statements and one allocation kind, over an **opaque tile** (a value with a shape and an element type and **no per-lane mapping**):

```text
Allocation space  MemorySpace::Tile   // one 8x8 (or m x n) tile per subgroup; no element is addressable, only the tile statements reach it
Stmt::TileLoad  { d: u32, src: Place, elements_per_row: ScalarExpr, origin: [ScalarExpr; 2], transpose: bool }
Stmt::TileMma   { d: u32, a: u32, b: u32, c: u32, saturate: bool }   // D = A.B + C on tiles; d may be c; `saturate` is WMMA's `satf`
Stmt::TileFill  { d: u32, value: ScalarExpr }               // fill_fragment / make_filled_simdgroup_matrix (a diagonal matrix is a fill plus a mask, not built)
Stmt::TileStore { a: u32, dst: Place, elements_per_row: ScalarExpr, origin: [ScalarExpr; 2], transpose: bool }
```

The tile's element type and shape live on its `AllocDecl` (`TileShape { m, n, k, elem, acc }`); Apple's is 8 x 8 x 8 with `half`/`bfloat`/`float`. `src`/`dst` are `Shared` or `Global` places (MSL's `threadgroup` and `device` address spaces). All three are rendezvous statements reached in uniform control by the whole subgroup (a `TileMma` on divergent lanes is the same kind of error as a divergent `Mma`). `origin` and `elements_per_row` carry MSL's `matrix_origin` and `elements_per_row` (default `Cols`; WMMA's `ldm`); `transpose` carries `transpose_matrix` (WMMA spells the same thing with `row_major` / `col_major`, on the fragment for `matrix_a`/`matrix_b` and as `mem_row_major` / `mem_col_major` for an accumulator).

**What the oracle computes.** The tile is a small matrix held once per subgroup, never per lane. `TileLoad` reads `m x n` elements from `src` (row `r`, column `c` at `src + (origin.y + r) * elements_per_row + origin.x + c`, or the transpose) as ordinary logged loads **attributed to the subgroup's first lane** (so the race detector sees one reader, not 32; a barrier orders it like any other); `TileMma` forms `D = A.B + C` with exact products summed in `f64` and rounded once to the accumulator type, exactly as `Mma`'s oracle does; `TileStore` writes the tile back as logged stores by the first lane. No thread-to-element mapping appears anywhere, so the CPU oracle runs it and a device may use whichever distribution it likes: the contract is the *result tile*, compared within the `Mma` tolerance for floats.

**Differences from `Mma`.** `Mma`: per-lane `Private` fragments, layouts in the atom, the program can read and write individual fragment slots (the epilogue code that scales or converts `D` lane by lane). `TileMma`: no fragment slots, the program cannot touch an element between `TileLoad` and `TileStore` (Metal offers no way to either: `simdgroup_matrix` has no documented element access). Elementwise work on an Apple tile must go through `Shared` (store, `Barrier`, load), which is what Metal code does.

## 3. Does CUDA's WMMA share it? Yes, with three differences (read 2026-11-25)

**CUDA Programming Guide, section 5.4.11.1 "Description" (`nvcuda::wmma`), read 2026-11-25:** "`fragment` An overloaded class containing a section of a matrix distributed across all threads in the warp. **The mapping of matrix elements into fragment internal storage is unspecified and subject to change in future architectures.**" Section 5.4.11.5 "Restrictions": "threads holding only a fragment (opaque architecture-specific ABI data structure) of the overall matrix, with the developer not allowed to make assumptions on how the individual parameters are mapped to the registers participating in the matrix multiply-accumulate", and a fragment is unsafe to pass between functions compiled for different link-compatible architectures ("sm_70 and sm_75" differ), so "the matrix should always be stored out to memory for transit". Section 5.4.11 intro: "This requires co-operation from all threads in a warp. In addition, these operations are allowed in conditional code only if the condition evaluates identically across the entire warp, otherwise the code execution is likely to hang." `load_matrix_sync`: "This function must be called by all threads in the warp, or the result is undefined", with `mptr` "a 256-bit aligned pointer", `ldm` "the stride in elements between consecutive rows (for row major layout) or columns" and "must be a multiple of 8 for __half element type or multiple of 4 for float element type", and "The values of mptr, ldm, layout and all template parameters for a must be the same for all threads in the warp". `mma_sync`: "This function must be called by all threads in the warp, or the result is undefined", `satf`: "If an element result is +Infinity, the corresponding accumulator will contain +MAX_NORM ... If an element result is NaN, the corresponding accumulator will contain +0".

**So WMMA is the same opaque-tile class as Apple's `simdgroup_matrix`: the element-to-thread mapping is unspecified in both, both are warp/SIMD-group-uniform load / multiply-accumulate / store, and both go through memory for anything per-element.** One statement family serves both; that is the strongest evidence this lane can give for the Q1 brief. WMMA's shapes and types (section 5.4.11.6): `__half` x `__half` into `float` or `__half` at 16x16x16, 32x8x16 and 8x32x16; `signed`/`unsigned char` into `int` at the same three; `__nv_bfloat16` into `float` at the same three; `precision::tf32` into `float` at 16x16x8; and a double-precision and sub-byte (preview) section whose rows were not read. Apple's is 8x8 with `half`/`bfloat`/`float` (so `TileShape` is `{ m, n, k, elem, acc }`, not 8x8 fixed).

**The three differences the statements must carry:**
1. **A `Use` per fragment.** WMMA types a fragment as `matrix_a` (m x k), `matrix_b` (k x n) or `accumulator` (m x n) and puts `row_major` / `col_major` on the multiplicands; Apple's `simdgroup_matrix<T,Cols,Rows>` is one type for every role (the shape rules of `simdgroup_multiply_accumulate`, `<T,K,Rows>& a`, `<T,Cols,K>& b`, carry the role). The `TileShape` therefore carries a `use` (`A`, `B`, `Acc`, or `Any` for Apple).
2. **`satf`** exists only in WMMA's `mma_sync` (`TileMma.saturate`); Apple has none.
3. **A narrow element-access escape in WMMA only:** "In the special case where all threads in the warp will apply an element-wise operation uniformly to all fragment elements, direct element access can be implemented using the following fragment class members. `enum ...::num_elements; T ...::x[num_elements];`" (section 5.4.11.1). It is **not** a mapping: every thread applies the same operation to all its own `x[i]`, so the result is independent of the mapping. The tile design models it as an elementwise statement (`TileMap { d, a, f }`, one `ScalarExpr` over one element, applied to every element of the tile) and **does not expose `x[]`**; a lowering for WMMA spells the `for (i < num_elements) x[i] = f(x[i])` loop, a lowering for Metal goes through `Shared` (Apple documents no element access). Not built, named so the Q1 decision sees it.

ThunderKittens' register tiles and CuTe's `Tensor`/`TiledMma` are different: they carry a `Layout` and per-thread partitions, so they are the larger part of Q1 and are not what this note proposes. A lead for Q1, not read: the CUDA Programming Guide now has a page "Writing Tile Kernels" (`02-basics/writing-tile-kernels.html`) listed in its table of contents; NVIDIA's own tile programming model is evidence for option A.

## 4. What each Q1 option needs (the evidence for the brief)

Q1 (`docs/ir-union-rulings.md`): **A** a tensor/tile value in the IR; **B** recipes over `Alloc` + `Layout` with a scoring rule; **C** a layout on allocations plus partition vocabulary (the recommended C, then A only for rows C cannot reach).

| Option | Does it carry the opaque tile statements? | Cost |
|---|---|---|
| **A** tensor/tile value | **Yes, naturally**: the Apple tile is a tile value whose layout is "opaque"; `TileLoad`/`TileMma`/`TileStore` are the tile-granular moves and `TiledMma` of A, with the layout leaf left opaque. | none beyond A (the three statements become instances of A's general ops) |
| **B** recipes | **No**: a recipe over `Alloc` + `Layout` has no object that exists only inside registers with no addressable element; the tile cannot be expressed as an allocation with a layout. | it would need an exception: a fixed "opaque tile" statement family outside the recipe scoring |
| **C** layout on allocations + partition | **No**: C describes where elements live; the opaque tile has no elements to place. | same exception as B: the three statements and `MemorySpace::Tile` as a stand-alone family |

**So the statement family is not common to every Q1 option**: under A it is a case of the general design; under B or C it is a small, self-contained exception (three statements, one space). **It needs A, or an explicit exception under B/C; it cannot be reached from a layout vocabulary alone.** Building the exception first would not foreclose A (the three statements are what A's general ops reduce to for an opaque layout), but it would make the Q1 answer matter less for Metal and leave the CUDA WMMA and ThunderKittens question as it is, which is why pm-kernels held the build for the ruling.

## 5. Cost and breakage

New `Stmt` variants (4: `TileLoad`, `TileMma`, `TileStore`, `TileFill`; `TileMap` only with the WMMA lowering) and a new `MemorySpace` variant: **BREAKING** for every exhaustive match (`unpopped-convert`, `unpopped-cpu-c`, the Baracuda and Vulkane emitter crates); batch with the U8c lineage (Q14 A). Slices, red-first: (1) `MemorySpace::Tile` + `TileShape` + checker (uniform control, subgroup of 32, element types, `Shared`/`Global` places); (2) oracle for the three statements with the differential against a hand-written product; (3) the serial C (the CPU reference can run it: a tile is a small array); (4) `TileFill` and the `saturate` flag; (5) the lift from the C frontend (`simdgroup_load` and friends are Metal source, which the C-family walker does not read today: a Vulkane/Slang-side matter).
