## 2. Brief for CireSnave: should the IR have a tensor or tile value type?

**The plain version.** Several kernel languages, above all CuTe and ThunderKittens, treat a "tensor" or a "tile" as one value: a block of numbers with a shape and a memory layout that you can slice, split among threads, and hand to a matrix-multiply or copy instruction as a unit. Unpopped's IR today has no such value. A kernel in Unpopped works with allocations (`Alloc`, shared or private), with `Layout` (the layout algebra, which is finished and tested), and with per-thread statements; a "tile" is an allocation plus a layout plus arithmetic that the person or front end writes out. The question is whether the IR should gain the tile as a value of its own, or whether tiles should stay as recipes built from allocations and layouts. This is yours because it is the largest design choice left in the union and it cannot be undone cheaply.

**What it gates.** Twenty-four rows that are not yet a full Yes: CuTe 3, 15, 17, 22, 23, 24, 25, 26, 27, 30, 31, 40, 47 and 66 (fourteen rows), ThunderKittens 1, 2, 3, 5, 6, 38 and 39 (seven rows), Mojo 38, and Slang 25 and 26. No ROADMAP row covers the question today, and the ROADMAP's own stance (ruled for pipelines in U8 S4) is "recipes, not nodes", so a silent default exists, but it has never been ruled for tiles.

**Why it matters under your standard.** On 2026-11-11 you said that if Unpopped's IR does not support something one of those kernel languages is capable of, the IR is not yet complete to your standards. A recipe can make a program expressible, because a CuTe partition is only index arithmetic that an emitter would lower anyway. But a recipe does not make the language's own form of the program expressible: the front end must write the arithmetic out itself, the IR does not know that two statements together are "a partition", and an emitter for a target with a native tile type cannot see it. Whether that counts as "supports" under your standard is a call only you can make, so the options below say what each one would let us score.

**Option A: a tensor/tile value in the IR.** The IR gets a value that carries element type, memory space and a `Layout`, plus the operations CuTe and ThunderKittens use on it (slice, local tile, per-thread partition, retile, TiledMma and TiledCopy objects, layout conversion, tile-granular moves). It unblocks all 24 rows. It is the largest change: the kernel statement set, the checker, the oracle, the serial C emitter, the text codec and the structure key all change, and every emitter that reads the IR changes too, so it is a breaking release that Baracuda, Vulkane, fishstringer and openclownfish each have to absorb. We estimate 14 to 20 PRs for Unpopped (the CuTe and ThunderKittens estimates overlap), plus a migration for each consumer, and a patent re-read for the tile and partition constructs, which we have not searched.

**Option B: recipes, with a stated scoring rule.** You rule that a tensor or tile is a recipe over `Alloc` and `Layout`, and that a row whose capability is reachable as such a recipe, and proven by a conformance kernel that runs it, counts as supported. It costs no IR change; the cost is the conformance kernels (about 6 to 8 PRs, the same kind of work as the GEMM-family kernels already planned) and the scoring rule, which is yours to approve. It would close 13 rows once each has its kernel: the partition and tiling rows (CuTe 22, 23, 24, 26, 27, 30, 31 and 47, ThunderKittens 6, 38 and 39, Mojo 38) and the "tensor value" row itself (CuTe 17) by the ruling. It leaves 11 rows open (CuTe 3, 15, 25, 40 and 66; ThunderKittens 1, 2, 3 and 5; Slang 25 and 26), because those need a vocabulary change (dynamic layout modes, a swizzled layout in a kernel, a layout as a property of a value) or a fragment value, not a recipe. The risk: it is a ruling that these rows are done without the IR knowing about tiles, which you may judge to fall short of your standard.

**Option C (the lane's recommendation): a layout on allocations and partition vocabulary, then a value type only for what remains.** Two additive changes: an allocation may carry a `Layout` (with dynamic modes, so CuTe 3 and 66 and Mojo 38 are reached), and `unpopped-vocab` gets the partition and tiling functions as pure vocabulary with property tests, as the layout algebra already is, followed by conformance kernels that use them. The rows it reaches are CuTe 3, 15, 22, 23, 24, 25, 26, 27, 31, 47 and 66, ThunderKittens 2, 5, 6 and 38, and Mojo 38, and it closes CuTe 17 with the ruling that the layout-carrying allocation is the tensor. What it does not reach, and what would still need Option A's value type later if you want it, is the TiledMma and TiledCopy objects (CuTe 30, 40), a tile as a register-resident fragment value (ThunderKittens 1, 3 and 39) and the tile-granular cooperative-matrix operations (Slang 25 and 26). We estimate 8 to 11 PRs: one or two for the layout field (additive, with a serde default), two for dynamic layout modes, four or five for the partition vocabulary with kernels, one for subtile views. It keeps the door open: nothing in C has to be undone if you later choose A for the remaining rows.

**The recommendation, and why.** Option C. It reaches 17 of the 24 rows at about half the cost of A, it is additive (no consumer breaks), and it puts the layout algebra, which is finished and tested, to its first real use in a kernel. The remaining seven rows are the ones where the tile is a first-class fragment value; that is the part that needs a hardware-near design (register fragments, atom layouts), and it is better decided after C has shown what the consumers (Baracuda's sm_90 emitter, the CuTe-style front ends) actually ask for.

## 3. Why three rows moved DOWN

- **CUDA 60 (block-scaled `F8E8M0`): a corrected earlier score, not a regression.** The Yes at a634b09 and 78c7d38e overstated it: the plan gate refuses `F8E8M0` by name as a scale type (`plan/dtype_float.rs`, checked by hand for this note), and only e4m3 and e5m2 run in the oracle. Nothing was removed.
- **Slang 31 (64-bit atomics): a corrected earlier score and a stricter reading.** The checker admits `I64`/`U64` and the oracle is generic over integers, but no test executes a 64-bit atomic: the only `I64` hits in `kernel_atomic_{rmw,cas,fetch}.rs` are refusals (checked by hand; the same grep finds 18 `I32` uses in `kernel_atomic_rmw.rs`). The earlier evidence named the checker rule, not a run; one 64-bit atomic test (about 0.1 PR) would restore the Yes.
- **Slang 51 (rounding mode per op): a deliberate safety fix, read strictly.** #388 (merged 2026-11-23) made `check_kernel` refuse `Qualified` operations at F64 and the half types by name (`TypeError::IllegalQualifier`, `tests/kernel_qualified_dtype.rs`); before it, such a kernel passed the checker and the oracle panicked, so the old Yes overreached for `__dadd_rn`-style operations. The capability on conversions (`RoundMode`, `Saturation` on `Cast`) still runs at every dtype. The remaining gap is ROADMAP U43.
