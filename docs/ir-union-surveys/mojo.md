## IR facts established (ir.rs @ a575e66)
- Access variants: Elementwise, Reduction, RowReduce, Contraction, Scan, Window, RowSort, Im2Col (all `#[non_exhaustive]` enum). No Attention. No Tile/Cooperative node.
- Contraction: `ContractionAxes::batched_matmul()` exists (rank-3 B,M,K x B,K,N) - so "rank-2 only" in the brief is slightly stale; one ContractedK axis; AccumSpec has a single variant `WideFloat`; ReductionAccum has single variant `Auto`.
- ScalarExpr leaves: Input, Const, Param, Reduced, Coord; ops Add/Sub/Mul/Div, Unary, Binary, Select (float-only). No let/loop/call/vector/lane/thread-id nodes.
- ReadIndex {Direct, Indexed(gather)}, WriteIndex {Direct, ScatterIndexed}, WriteCombine {Assign, AtomicAdd, AtomicMax, AtomicMin}; View {Identity, Permute, Broadcast, Reshape}.
- Schedule (plan.rs) {Vectorized{width}, Scalar, Strided, Reduction, RowReduce{block}, Contraction, Scan{block}, ...} - cooperation exists ONLY as an emitter-chosen schedule, never as IR (idiom-lifting-design.md lines 71-83: "the IR never models cooperation" - now overridden by the owner ruling).
- ElementKind (element.rs ~1050-1230): F16 Bf16 F32 F32Strict F64 I8 I16 U8 U16 I32 I64 Bool Fp8E4M3FN Fp8E4M3FNUZ(reserved) Fp8E5M2 Fp8E5M2FNUZ(reserved) F8E8M0 F8E6M2(reserved) I4 U4 B1 Complex64 Complex128 U32 U64. MX element formats f4/f6e2m3/f6e3m2 deliberately NOT ElementKind ("block-scoped element formats living in the MX-encoding vocabulary", element.rs 1148-1153). No f8e3m4.
- Grep counts in ir.rs (case-insens): barrier 0, warp 0, shuffle 0, cluster 0, async 0, thread/blockIdx 0, "Tile" 0; "shared"(29)/tma(6)/mma(6) are doc-comment mentions (not checked line-by-line). Positive control: `Atomic` family and `ReadIndex` found.

## (2) Ten highest-impact gaps (ordered)

1. Hierarchical Layout algebra + Swizzle as IR values (View has only Permute/Broadcast/Reshape). Nothing shared-memory or tensor-core related can be described faithfully without it; it also underlies TMA descriptors and fragment maps.
2. Memory spaces and scratch allocation (Shared, Local/Register, Constant, SharedCluster, TMEM) with explicit buffers; today every operand is a flat global tensor.
3. Execution-hierarchy ids and launch grid (thread/block/cluster/lane/warp ids, block/cluster dims). Without per-thread identity there is no way to write cooperative code; `Coord` is output-element only.
4. Statement layer: local variables, bounded/unbounded loops, runtime if, load/store with predicate, calls. The IR is a pure per-coordinate expression DAG; Mojo kernels are imperative.
5. Barriers and fences with scope (warp, block, cluster, grid) and mbarrier/named barrier objects with phase parity; plus the memory-ordering model for them.
6. Tensor-core tile ops: warp mma + ld_matrix/st_matrix fragments, wgmma async group (issue/commit/wait), tcgen05/UMMA with TMEM accumulators; AccumSpec still has one variant.
7. Async copy and TMA: cp.async groups, cp.async.bulk, cp.async.bulk.tensor (load/store/reduce/multicast/im2col/gather4) with tensor-map descriptors and multi-stage pipeline state.
8. Warp/block/cluster collectives as composable expression nodes (shuffle x4, vote/ballot, match, elect, lane_group_*, block.sum/max/min/prefix_sum/broadcast, cluster allreduce/allgather); today only reachable as whole-op Reduction/RowReduce/Scan schedules.
9. Full atomics: CAS (strong/weak), exchange, and/or/xor, returned old value, ordering, scope, usable on shared and global; today only AtomicAdd/Max/Min inside ScatterIndexed.
10. Dtype/numerics: float4_e2m1fn / float6_e2m3fn / float6_e3m2fn / float8_e3m4 as first-class element types (IR deliberately keeps MX element formats out of ElementKind), FNUZ fp8 compute semantics (reserved), mixed A/B/accumulator dtypes on Contraction, vector-typed SIMD values with shuffle/interleave/reduce.

Next tier: custom (user-lambda) reduce ops and tuple accumulators, cluster launch control/PDL, device-wide semaphore, cache-hint/scope attributes, multimem.

## (3) Possible errors or tensions in the IR relative to Mojo (and the brief)

- idiom-lifting-design.md lines 71-83 state "the IR never models cooperation" and tell parsers to lift cooperative source to non-cooperative intent; the residue refusal of `__shared__`/`__shfl`/`__syncthreads` encodes that. This directly contradicts the owner ruling and Mojo's model (explicit `barrier()`, `stack_allocation[AddressSpace.SHARED]`, `warp.shuffle_*`). Needs a design-doc reversal, not just new nodes.
- The "not transferable" list in the same doc (cp.async, TMA/wgmma, clusters/DSMEM, warp-specialised named barriers) is exactly what Mojo's `gpu` package exposes as first-class API (max/gpu/memory, max/gpu/sync, max/gpu/primitives/cluster, max/layout/tma_async). Under the new ruling these become nodes with capability gating.
- element.rs 1148-1153 excludes f4/f6 from ElementKind ("maintainer ruling 2026-08-08"); Mojo's DType has float4_e2m1fn, float6_e2m3fn, float6_e3m2fn as first-class dtypes. That ruling conflicts with the union rule and needs revisiting. Mojo also has float8_e3m4, absent in ElementKind.
- Mojo `float8_e4m3fnuz`/`e5m2fnuz` have real hardware support on AMD (get_amd_fp8_dtype); the IR holds them as RESERVED with no compute semantics.
- `ScalarExpr::Select` is float-only (ir.rs doc); Mojo `SIMD.select` works on any dtype and Mojo integer masks are common in kernels. Integer select is rejected "outright" in v1.
- `Coord(axis)` rejects f16/bf16/int and every non-Elementwise Access; Mojo thread/block ids are Int-typed values usable anywhere - the Coord design (float cast, Elementwise-only) is too narrow to serve as the thread-id leaf.
- The brief says Contraction is rank-2; ir.rs has `ContractionAxes::batched_matmul()` (rank-3 with Batch). The Contraction doc comment still says "v1: rank-2" - stale doc or the batched form is only partially wired (plan validation not read).
- `index_dtype` limited to I32/I64 (ReadIndex); Mojo indexes with machine-word `Int`/`UInt` and Coord-based mixed static/runtime ints.
- Mojo 1.x renamed `@parameter if/for` to `comptime if/for` and `fn` to `def` in newer docs; any Unpopped Mojo front-end should accept both spellings. LayoutTensor is being superseded by TileTensor (Coord-based layouts, runtime dims, TileTensorIter), which "doesn't yet implement all LayoutTensor features" - a front-end should target the layout algebra (`layout` module), not the tensor wrapper type.
