# CUDA C++ (nvcc/NVRTC + PTX reachable) vs Unpopped IR: gap survey

IR read at origin/main: `crates/unpopped/src/ir.rs` (4300 lines; line refs below are into that blob), `unpopped-vocab/src/{element,plan,layout,ops}.rs`, `crates/unpopped/src/plan.rs`, `docs/idiom-lifting-design.md`.
Baseline IR facts (verified by reading the enums): ScalarExpr = {Input, Const(f64), Param, Reduced, Coord, Add, Sub, Mul, Div, Unary, Binary, Select} (ir.rs:63-135). No Cast node, no Fma node, no let/loop/vector value. Access = {Elementwise, Reduction, RowReduce, Contraction, Scan, Window, RowSort, Im2Col} (ir.rs:1607). Contraction carries only `ContractionAxes` (roles Batch/FreeM/FreeN/ContractedK), `AccumSpec::WideFloat` (sole variant, ir.rs:1928), epilogue ScalarExpr. View = {Identity, Permute, Broadcast, Reshape} (ir.rs:1973). ReadIndex = {Direct, Indexed{index_operand,axis,oob,index_dtype}} (ir.rs:2099). WriteIndex = {Direct, ScatterIndexed{..combine: Assign|AtomicAdd|AtomicMax|AtomicMin}} (ir.rs:2202-2256). Schedule (plan.rs:26) = Vectorized/Scalar/Strided/Reduction/RowReduce/Contraction/Scan/...; no tile/stage/cluster parameters. ElementKind (25 kinds, element.rs:471) = F16 Bf16 F32 F32Strict F64 I8 I16 U8 U16 I32 I64 Bool Fp8E4M3FN Fp8E4M3FNUZ Fp8E5M2 F8E8M0 F8E6M2(reserved) Fp8E5M2FNUZ I4 U4 B1 Complex64 Complex128 U32 U64. MathPrecision (element.rs:535) includes Tf32 as a precision label only.
Grep controls (ir.rs, case-insensitive): barrier=0, warp/shfl/ballot=0, cluster=0, swizzle=0, fp4/fp6/E2M1/E3M2/nvfp4=0, persistent/stream-k/split-k=0; positive controls: "Reduced" and "Indexed" hit many times. Hits for shared/cp.async/mma/sparse/loop are comments only (e.g. ir.rs:1916, 1931 forecast "Tensor-core/TF32 policies join as variants"; no such variant exists).

## 2. Ten highest-impact gaps (ranked by how much of the language each unlocks)

1. No explicit mutable on-chip memory: shared / local / constant / tensor / distributed-shared spaces, with typed load/store and indexed addressing. Everything cooperative needs this.
2. No synchronization model: block/warp/cluster/grid barriers, mbarrier (phases, transaction counts, split arrive/wait), fences with proxy, async groups.
3. No thread-level execution model: no thread/lane/warp/block id leaves, no groups (tiled/labeled/binary partition), no predicate or divergent control, so no warp shuffle/vote/match/redux.
4. No tile-level tensor-core ops: fragments, `wmma`/`mma.sync`/`mma.sp`/`wgmma`/`tcgen05` with shape, accumulator, sparsity, block-scale metadata. `Contraction` is semantic-only, `AccumSpec` has one variant, tile shape is absent from `Schedule::Contraction`.
5. No async data movement: `cp.async`, TMA (bulk 1D, tensor <=5D, multicast, reduce), tensor maps, swizzle, `ldmatrix/stmatrix`.
6. No control flow in the expression language: no loops, no `If` regions, no early exit, so no data-dependent loops, persistent tile loops, or in-kernel online algorithms (flash attention, which also has no Access::Attention).
7. No scheduling vocabulary: pipeline stages, warp specialization roles, persistent/stream-K/split-K scheduler, cluster shape, `setmaxnreg`, launch bounds.
8. Atomics and memory model: only 4 scatter combines (Add/Max/Min plus Assign), no CAS/Exch/And/Or/Xor/Inc/Dec, no returned old value, no scope (thread/block/cluster/device/system), no memory order, no atomics on shared memory.
9. Dtype and vector gaps: fp6 (e2m3, e3m2), fp4 (e2m1/NVFP4), TF32 as a Contraction input, `half2/bfloat162/float4` packed values, 128-bit ints/floats; no Cast node with rounding/saturation.
10. Numerics controls: no explicit FMA node, no rounding-mode suffix, no ftz/denormal flag, no approx-vs-exact qualifier on transcendentals, no dp4a-style I32Wrap/I32Sat accumulators. All currently only planned in prose (idiom doc section 3.1), none in ir.rs.

## 3. Things in the IR that are wrong or misleading relative to CUDA

a) `docs/idiom-lifting-design.md` section 1a (lines ~69-91) states: "no, the IR never models cooperation". This is the opposite of the owner's ruling. It also states the residue refusal of `__shared__/__shfl/__syncthreads` becomes "refuse only if no recognizer claims it". Both need replacement (a retraction must reach as far as the claim did). The same doc table in section 1 cites `Schedule::RowReduce` "warp-shuffle + shared-memory tree" as the cooperation model; that is an emitter schedule, not an IR concept the frontend can express.
b) `WriteCombine::is_fp_atomic_add` (ir.rs:2221-2234) uses a private `is_integer_kind` that lists only `I32 | I64 | U8 | I8`. `ElementKind` also has `I16, U16, U32, U64` (and `I4/U4`, `Bool`), so `AtomicAdd` on `U32`/`U64`/`I16`/`U16` is classified as a floating-point atomic. For CUDA that matters: `atomicAdd(unsigned*)` is a deterministic integer atomic, and the flag feeds determinism claims. I verified only the function and its unit tests (ir.rs:3776-3803); I did NOT trace callers, so the downstream effect is unconfirmed.
c) `ScalarExpr::Coord` is restricted to `F32/F32Strict/F64` (ir.rs:~120-135 doc). CUDA code uses integer `threadIdx/blockIdx` arithmetic everywhere; the float-only coordinate cannot carry integer index math, so index-heavy kernels cannot be lifted until an integer coordinate exists. The doc itself calls the int spelling "the queued follow-up".
d) `Select(c,a,b)` is a pure ternary; CUDA `?:` and `if` evaluate only one arm, which matters when an arm would trap or fault (division by zero in int, out-of-bounds load). Whether the emitter preserves lazy evaluation is UNVERIFIED (not traced); the IR doc does not say.
e) `AccumSpec`/`ReductionAccum` docs (ir.rs:1916, 1931) promise "Tensor-core/TF32 policies join as variants", and `MathPrecision::Tf32`, `Fp8*` exist in the vocab. A reader will assume tensor-core accumulation is representable; the IR has exactly one variant (`WideFloat`) and `#[non_exhaustive]`.
f) `ElementKind::Fp8E4M3FNUZ`, `Fp8E5M2FNUZ` and `F8E6M2` are not CUDA types (CUDA names are `__nv_fp8_e4m3`, `__nv_fp8_e5m2`, `__nv_fp8_e8m0`, fp6/fp4 per the math-functions page). `F8E6M2` is marked reserved (commit 5136250). Not wrong, but they carry no CUDA mapping while the actual CUDA fp6/fp4 types are missing.
g) `Window.size/stride/dilation/pad_*` are `u8` and `Im2Col` params are `u8` (ir.rs:1688+): CUDA kernels take arbitrary `int` strides and window sizes; >255 sized windows (e.g. 1D pooling over long axes) cannot be expressed. Plausible latent limit; not traced further.
h) Note on sources: the CUDA Programming Guide pages fetched did not themselves list `atomicCAS/Exch/...`, `__shfl_*_sync`, `__threadfence`, `__launch_bounds__`, or the inline-asm constraint syntax; those entries are marked UNVERIFIED and should be confirmed in the legacy guide (https://docs.nvidia.com/cuda/cuda-c-programming-guide/) before any spelling goes into a registry.
