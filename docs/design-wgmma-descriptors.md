# Design note: shared-memory layout fields for `Stmt::Wgmma` and `Stmt::Tcgen05Mma` (ROADMAP U8c, Baracuda's ask)

Status: **design, not built.** Written 2026-11-25 by the Unpopped lane on pm-kernels' relay of Baracuda's `[ASK]`. The build waits for Baracuda's review of this note. The IR change is **BREAKING** for `unpopped` (new fields on two `Stmt` variants): batch it with the next breaking release (Q14 A). Nothing here is legal advice.

## 1. The ask

`Stmt::Wgmma` (and `Tcgen05Mma`) say "option A: no swizzle and no descriptor bits are modelled, and there was no ISA text to check them against". An emitter cannot build the 64-bit matrix descriptor from them. Per operand it needs a swizzle mode, the leading and stride byte offsets (or a core-matrix layout), the base-offset and alignment contract, and MN-major (transposed) support, with the **oracle reading through that layout**. A plain row-major K-major 16-bit tile is not a layout the no-swizzle descriptor reads. Baracuda will not guess bits: until these fields exist it refuses both statements by name.

## 3. What the ISA says (the facts the fields come from)

**`wgmma` matrix descriptor** (64 bits, 9.7.17.5.1.2.2): bits 13-0 `matrix-descriptor-encode(start address)`; 29-16 `encode(leading dimension byte offset)`; 45-32 `encode(stride dimension byte offset)`; 51-49 "Matrix base offset. This is valid for all swizzling modes except the no-swizzle mode."; 63-62 swizzle ("0: No swizzle 1: 128-Byte swizzle 2: 64-Byte swizzle 3: 32-Byte swizzle"). `matrix-descriptor-encode(x) = (x & 0x3FFFF) >> 4`. Base offset is 0 when the repeating pattern starts on a 1024 (128B), 512 (64B) or 256 (32B) byte boundary; otherwise `(pattern start addr >> 0x7) & 0x7`. "The contents of a matrix descriptor must be same across all the warps in the warpgroup."

**Layouts** (canonical, CuTe notation, `T = 128 / sizeof_bits(element)`, 8 for 16-bit): K-major none `((8,m),(T,2)):((1T,SBO),(1,LBO))`; K-major 32/64/128B `((8,m),(T,2)):((2T|4T|8T,SBO),(1,T))` (LBO "not used, assumed to be 1"); MN-major none `((T,1,m),(8,k)):((1,T,SBO),(1T,LBO))`; MN-major 32/64/128B `((T,2|4|8,m),(8,k)):((1,T,LBO),(2T|4T|8T,SBO))`; each under `Swizzle<0|1|2|3,4,3>`. Stride offset: K-major "the offset from the first 8 rows to the next 8 rows"; MN-major swizzled "offset from the first 8 columns to the next 8 columns". Leading offset: K-major none "the offset from the first column to the second columns of the 8x2 tile"; MN-major swizzled "offset from the first (swizzle-byte-size/16) rows to the next (swizzle-byte-size/16) rows".

**Transpose:** "The transpose operation is only supported for the wgmma.mma_async variants with .f16/ .bf16 types on matrices accessed from shared memory using matrix descriptors"; `imm-trans-a/b` 0 means K-major, 1 means M-major (A) or N-major (B). With `A` in registers there is no transpose operand for `A`.

**`D` fragment** `m64nNk16`, `.f32`: N/2 registers `d0..`; **(figure)** warp `w` holds rows `16w..16w+15`, register `i` of lane `l` is row `16w + l/4 + 8*((i/2)%2)`, column `8*(i/4) + 2*(l%4) + i%2`. This is the formula `oracle/kernel_wgmma.rs::position` already uses, now cross-checked against the figure.

**tcgen05** shared-memory descriptor (9.7.18.4.1) is **not** the same word: 15-bit start address (bits 0-14), 15-bit leading offset (16-30), stride offset (32-45), bits 46-48 the fixed constant `0b001`, base offset 49-51, a leading-stride-mode bit 52 (absolute byte address mode is sm_103a only, 128B swizzle, K-major only, base offset 0), bits 61-63 swizzle with **different codes** ("0 No swizzling, 1 128-Byte with 32B atomic swizzling, 2 128-Byte, 4 64-Byte, 6 32-Byte; 3, 5 and 7 are invalid"). The layouts and the LBO/SBO meanings are the same as `wgmma`'s. Instruction descriptor (32 bits, 9.7.18.4.2, table cells flattened so partly inferred): bits 4-5 D type, 7-9 / 10-12 A / B type, 13/14 negate, 15/16 transpose A/B, 17-22 `N >> 3`, 24-28 `M >> 4`. Tensor memory: 128 lanes x 512 columns of 32 bits per CTA; address = lane in bits 31:16, column in 15:0; allocation unit 32 columns, a power of two, `tcgen05.alloc ... nCols` in [32, 512]; every allocation must be deallocated before exit; `tcgen05.alloc` is illegal after `relinquish_alloc_permit`. A CTA pair is two CTAs whose `%cluster_ctarank` differ in the last bit; all `tcgen05` instructions in a kernel use one `cta_group`.

## 4. The design

**One new value type, shared by both statements** (`crates/unpopped/src/kernel.rs`):

```text
OperandLayout =
    RowMajor                                  // today's meaning: a plain row-major tile, pitch = K (16) elements
  | Canonical { major: Major, swizzle: Swizzle, lbo: Option<u32>, sbo: u32 }
Major   = K | MN                              // imm-trans 0 | 1
Swizzle = None | B32 | B64 | B128             // the PTX layout family; tcgen05's wire codes are the emitter's
```

`Stmt::Wgmma` and `Stmt::Tcgen05Mma` gain `a_layout` and `b_layout: OperandLayout` (`#[serde(default)]` = `RowMajor`, so stored text from before parses). `RowMajor` keeps every current test meaning and is **oracle-only**: an emitter for hardware refuses it with the reason "a plain row-major tile is not a layout the descriptor reads" (this is Baracuda's by-name refusal, now stated in the IR). `Canonical` is what an emitter lowers.

- **Offsets are bytes** (`lbo`, `sbo`), multiples of 16, below `2^18` (the 14-bit field times 16; tcgen05's leading field is 15 bits, so it may exceed `2^18`: the checker takes the stricter bound for `Wgmma` and the wider one for `Tcgen05Mma`). `lbo` is `None` for a swizzled K-major operand (the ISA: "not used, assumed to be 1") and the checker rejects `Some` there; it is required elsewhere.
- **Base offset is not a field.** The checker requires the tile's start (allocation base plus a constant offset) to be a compile-time multiple of the swizzle's pattern boundary (1024 / 512 / 256 bytes; 16 for no swizzle), so the descriptor's base offset is 0. A start that is not provably aligned is `Unsupported`. *Question 1 to Baracuda: do you need a non-zero base offset (a tile that starts mid-pattern)? If so the field is `base_offset: u8`, the checker derives it with the ISA formula, and the oracle reads from the unaligned start.*
- **MN-major** (`Major::MN`) is admitted for `F16`/`Bf16` only, which is all the statements carry today (the ISA restricts transpose to those types). `A` from registers stays out of scope.
- **Extents.** For a 64 x 16 `A` and an `n x 16` `B` of 16-bit elements, K-major canonical needs `m = rows / 8` groups of 8 rows and `(T,2)` = two 16-byte core columns along K; MN-major needs `m = rows / (T * s)` patterns (`s` = 1, 2, 4, 8 for none, 32B, 64B, 128B) and `k = 2`. The checker computes them from the tile and refuses a layout whose offsets would make two elements share a byte or leave the allocation.
- **The oracle reads through the layout.** `kernel_wgmma.rs` replaces "row `t` of `A` is 16 contiguous elements" with `element(row, k) -> byte offset` from the canonical layout above, then the swizzle (`Swizzle<B,4,3>`: XOR of address bits `[4,4+B)` with bits `[7,7+B)` of the byte address; confirmed against Figures 159-168, section 5c). Every read is still an ordinary logged `Shared` load, so the race detector is unchanged.
- **`D` fragment:** unchanged (section 3, figure-checked).

**`Tcgen05Mma` additionally:** `m: 64 | 128` (the ISA lists 64 or 128 for `cta_group::1`; today it is fixed at 128); `cta_group` stays 1 (a pair is declined by name until asked); a new `Tcgen05Alloc { d, ncols }`, `Tcgen05Dealloc { d, ncols }` and `Tcgen05RelinquishPermit` replace "the allocation is static": `ncols` a power of two in 32..=512 equal to the allocation's columns, issued by one warp, every alloc deallocated before the kernel ends, no alloc after the permit is relinquished (checker rules, oracle traps). The descriptor words themselves (15-bit start, the `0b001` constant, the swizzle code table, the instruction descriptor) are **not IR**: they are the emitter's, computed from the fields above and the statement's types; the facts are recorded in section 3 so the emitter has a checked source.

## 5b. The two fences (Baracuda's review, 2026-11-25; text checked in PTX 9.5)

PTX 9.7.17.7.1: "wgmma.fence instruction establishes an ordering between prior accesses to any warpgroup registers and subsequent accesses to the same registers by a wgmma.mma_async instruction. Only the accumulator register and the input registers containing the fragments of matrix A require this ordering." It "must be issued by all warps of the warpgroup ... Before the first wgmma.mma_async operation in a warpgroup" and "Between a register access by a thread in the warpgroup and any wgmma.mma_async instruction that accesses the same registers ... Otherwise, the behavior is undefined." And: "An async proxy fence must be used to establish an ordering between prior writes to shared memory matrices and subsequent reads of the same matrices in a wgmma.mma_async instruction." (9.7.10.28.2: "Accessing the same memory location across multiple proxies needs a cross-proxy fence. For the async proxy, fence.proxy.async should be used".)

**Decision.** (1) **`wgmma.fence` is not an IR statement**: it orders register accesses only, the oracle lands `D` at the wait and has no register hazard to observe, so it is a hardware synchronisation the emitter derives (before every `Wgmma`, as Baracuda does). (2) **`fence.proxy.async` is an IR statement, `Stmt::ProxyFence { space: Shared }`** (the `.shared::cta` form; `.global` and `.shared::cluster` only when a statement needs them): it is a fact of the source (CUTLASS and CuTe kernels write it), it has oracle-visible meaning because the oracle models shared bytes, and a derived-after-every-store rule costs fences the author did not need. (3) **A missing proxy fence is an oracle trap, `MissingProxyFence`**: the oracle keeps, per `Shared` byte, whether the last write was by a generic-proxy store not yet followed by the writing thread's `ProxyFence`; a `Wgmma`, `Tcgen05Mma` or `CopyBulk` whose source reads such a byte traps. `CopyBulk` completion already carries the ISA's implicit generic-async fence ("The completion of a cp{.reduce}.async.bulk operation is followed by an implicit generic-async proxy fence"), so bytes it wrote are fenced. Cross-thread ordering is still the existing barrier and race rules; the proxy fence adds only the proxy dimension.

## 5c. The swizzle XOR, read from PTX ISA 9.5 Figures 159-168 (2026-11-25)

Source: the PTX ISA 9.5 PDF (`https://docs.nvidia.com/cuda/pdf/ptx_isa_9.5.pdf`, 1031 pages; the figures are on PDF pages 677-683, printed 663-669), pages rendered to images and **read as images, not text** (the figures carry no extractable text). Each figure is a grid in units of **128-bit (16-byte) elements**; the number in a cell is that logical element's **storage position** in units of 16 bytes (the text above them: "in units of 128b elements as shown by each colored cell"). Writing `i` for the M/N index and `k` for the K index of the cell, `p` for its number, and checking every cell I could read legibly:

| Figure | Layout | Grid read | Rule that reproduces every cell | As a byte-address XOR |
|---|---|---|---|---|
| 159 | MN-major 128B | 8 (M/N) x 8 (K) | `p = 8k + (i XOR k)` | `Swizzle<3,4,3>`: bits 4-6 ^= bits 7-9 |
| 160 | K-major 128B | 8 x 8 | `p = 8i + (k XOR i)` | `Swizzle<3,4,3>` |
| 161 | MN-major 64B | 4 x 8 | `p = 4k + (i XOR (k >> 1))` | `Swizzle<2,4,3>`: bits 4-5 ^= bits 7-8 |
| 162 | K-major 64B | 8 x 4 | `p = 4i + (k XOR (i >> 1))` | `Swizzle<2,4,3>` |
| 163 | MN-major 32B | 2 x 8 | `p = 2k + (i XOR (k >> 2))` | `Swizzle<1,4,3>`: bit 4 ^= bit 7 |
| 164 | K-major 32B | 8 x 2 | `p = 2i + (k XOR (i >> 2))` | `Swizzle<1,4,3>` |
| 165, 166 | MN-/K-major interleaved (no swizzle) | 1 x 8 / 8 x 1 | `p = k` / `p = i` | identity |
| 168 | MN-major 128B, `tf32` | 32 x 8 (4 elements per 16 B) | chunk of `i` XOR `k`, e.g. `(i=0,k=1) -> 36`, `(i=4,k=1) -> 32`, `(i=0,k=2) -> 72` | `Swizzle<3,4,3>` on the 16-byte chunk |
| 167 | K-major 128B, `tf32` | 8 x 32 | **not read**: too small to read at the rendering used (same rule as Figure 160 expected) | - |

**Reading:** a swizzle is `Swizzle<B,4,3>` on the **byte address** of the 16-byte chunk: XOR the `B` bits at bit 4 with the `B` bits at bit 7, `B` = 3 (128B), 2 (64B), 1 (32B), none for the interleaved layouts. The pattern repeats every 1024 / 512 / 256 bytes, which is why the base offset is 0 only at those boundaries (section 3) and why this design keeps the tile start pattern-aligned. Rows 8 deep for 128B and K-major 64B/32B, as the grids show. Every cell of Figures 159-164 and the sampled cells of 168 agree with the rule; the checks were by hand against the images.

## 5f. `cta_group::2`, Layouts A-C (2026-11-25; two methods for A and B, one for C; not built)

**PTX ISA 9.5 9.7.18.10.5.1-3, Figures 211-216 (pages 770-772), read as page images.** Layout A (`M` = 256, `::2`): A rows 0-127 on the even CTA of the pair (32 rows per warp, `warp-rank % 4` = 0..3), rows 128-255 on the odd CTA, 4x1 datapath; Figure 212 prints the odd-CTA addresses as `0x0080 .. 0x00E0`. Layout B (`M` = 128, `::2`, dense A, 2x2): rows 0-63 on the even CTA, 64-127 on the odd; within a CTA, rows 0-31 and 32-63 are warps 0 and 1 for the first half of N (columns 0..N/2-1, lane quadrants `0x0000`, `0x0020`) and warps 2 and 3 for the second half (columns N/2..N-1, quadrants `0x0040`, `0x0060`). Layout C (`M` = 128, `::2`, sparse A, half datapath, alignment 0 or 16): 16 rows per warp, rows 0-63 even CTA, 64-127 odd; addresses `0x0000|0x0010 .. 0x00E0|0x00F0`.

**Second method, CUTLASS `include/cute/atom/mma_traits_sm100_frag.hpp` (commit `5c179edeb3e2`, BSD-3-Clause, facts only), `tmem_frg<.., N_SM == 2, ..>::make`, read as text.** The tensor is partitioned *per SM*: the comment says "for UMMA_2SM_128xNx16, that M_MMA_SM will be 64" and `M_MMA` is that per-SM row count. `M_MMA == 128` (the `M` = 256 pair): atom `<128,N>:<1,128>`: row `r` of an SM's half is **lane `r` of that SM's own tensor memory**, column `n` is column `n`. This **resolves the Figure 212 ambiguity**: the odd CTA's row `128 + r'` is lane `r'` of the odd CTA's own TMEM (the figure's `0x0080..` is the pair-logical address of the second CTA's block, not a lane above 127). `M_MMA == 64`, `Interleaved` (the `M` = 128 pair, Layout B, "2x2"): atom `<64,<N/2,2>>:<1,<128,64>>`: row `r` (0..63 of the SM's half) is lane `r`, column `n` is column `n % (N/2)` at lane offset `64 * (n / (N/2))`. **That is Layout B as Figures 213-214 read: the two sources agree** (lane quadrants `0x0000/0x0020` for the first half of N and `0x0040/0x0060` for the second). `Duplicated` (a further `TmemAllocMode`, `<128,N>:<1,128>` with M_MMA 64) and `M_MMA == 32` ("1x4", `<32,<N/4,4>>:<1,<128,32>>`, Layout G-like) exist in CUTLASS and are not in Figures 211-216. **Layout C (sparse) is not a `tmem_frg` case here (sparse D alignment 0/16 rests on Figure 216 alone).**

**So the data path is known for A and B; not built.** Remaining blockers: (1) the IR needs a CTA-pair rule: issue from one thread of the pair, the peer CTA active, `D` split over two blocks' tensor memories; the cluster model exists (`SharedPeer`, `%cluster_ctarank`) but `BlockMem.tmem` is per block, so it needs a cluster-level TMEM view; (2) Layout C one method; (3) Baracuda: "`cta_group::2` only on request" (section 7, Q4), none yet. `f8f6f4` (section 5g) is independent of all of this.

## 5g. `.kind::f8f6f4` (2026-11-25; two methods for the type codes, one for everything else; not built)

**PTX ISA 9.5 Table 53 (page 728) and Table 50 (page 705), read as text; Table 54 (mxf8f6f4) and sections 9.7.18.10.4.2-4 (pages 764-768) read as text, Figures 202-209 (the 4- and 6-bit packings) NOT read.** `.kind::f8f6f4`: `atype`/`btype` are **separate 3-bit fields** (bits 7-9 and 10-12): E4M3 = 0, E5M2 = 1, E2M3 = 3, E3M2 = 4, E2M1 = 5, so A and B may differ (the table says "all input combinations of f8, f6 and f4"); D is F16 (0) or F32 (1); dense `K` = 32 per instruction (`K1` = 64 appears for `M` = 128/256 and a bit-29 `K` flag that is `sm_107f` and later, so not for sm_100), sparse `K` = 64/128; `M` 64/128 (`::1`), 128/256 (`::2`), `N` 8..256 step 8 (`::1`). **CUTLASS** `mma_sm100_desc.hpp` (BSD-3-Clause, facts only; the `MXF8F6F4Format` enum and the `a_format_`/`b_format_` comments at lines 179-207, 435-436) **gives the same codes: the two agree**. Both also say negate (bits 13-14) is valid here.

**What the IR has and lacks.** `ElementKind::Fp8E4M3FN` and `Fp8E5M2` exist (decode through `Val::Float`); **no FP6 or FP4 kind exists** (U47, not started). `Tcgen05Mma` and `Wgmma` take one `ab` for both operands and the checker admits only f16/bf16; the oracle's `K` is the constant 16 (`kernel_wgmma.rs:28`).

**Independent of board 501 (buildable now, each its own slice):**
1. `ab` split into `a_ty`/`b_ty` on `Tcgen05Mma` (BREAKING, rides the stack); admit `Fp8E4M3FN`/`Fp8E5M2` for dense, `acc` F32, `D` F32 (F16 D is a further slice, tensor-memory 16-bit words are unpacked per PTX 9.7.18.10.4.1).
2. `K` per input width (32 for 8-bit): the oracle's tile read, the `OperandLayout` check (`check_layout` rows are 16 B units, so one swizzle atom row holds 16 FP8 elements, not 8 halves) and the shared test reference offsets all change; this is the larger half.
3. Negate A / negate B as flags (valid for f16 as well; a small separate row).

## 5h. `.kind::mxf8f6f4` block scaling: which parts need board 501 (2026-11-25; PTX text only, one method; not built)

**PTX ISA 9.5 Table 54 (page 729), 9.7.18.10.7 "Block Scaling for tcgen05.mma" and Tables 70-71 (pages 779, 786-787), read as text; Figures 234-236 are NOT the scale layouts (234 and 235 are the swizzle chunk numbering, 236 a schematic of the product, all read as images); the scale layouts are Figures 237-274 (pages 788-814), of which 237 (A) and 257 (B), the `scale_vec::1X`/`block32`, `K` = 32/64 cases that `mxf8f6f4` uses, were read as page images at page-render resolution. No second source read.** The operation is `(A * scale_A) * (B * scale_B) + D`, with `scale_A` (`M x SFA_N`) and `scale_B` (`SFB_M x N`) "residing in Tensor Memory"; each row of `A` is cut into `SFA_N` chunks and each chunk is multiplied by the scale of its row (likewise per column of `B`). For `.kind::mxf8f6f4` the shape is `M x 1` and `1 x N` (`.scale_vec::1X`, equivalently `.block32`), the element types are E4M3, E5M2, E2M3, E3M2, E2M1 and the scale type is **UE8M0 only** (Table 71); the descriptor carries `Scale Matrix Type` bit 23 (UE8M0 = 1), a 2-bit scale-factor data ID for A (bits 29-30) and for B (bits 4-5), and `Matrix A Scale Factor Layout` bit 26 (32-lane = 0, 128-lane = 1, `sm_107f`+). "Scale factor for B matrix needs to be duplicated to all 32 lane partitions of tensor memory" (A's duplication is only needed when the scales are copied by `tcgen05.cp`, not for `tcgen05.st` on `sm_107f`).

**Independent of board 501:** the `mxf8f6f4` scale type is **E8M0, which the IR already has as `ElementKind::F8E8M0`**; the 501 tokens (`ue4m3`, `ue5m3`) are the `mxf4nvf4` scale types only. So `mxf8f6f4` with FP8 data (E4M3/E5M2) needs no new token.

**What Figures 237 and 257 show (one method, read at render resolution, byte-level labels not all legible).** `scale_A` (A, 32-lane form): a `M` = 128 tile is four tensor-memory columns `X .. X+3`; column `X + c` holds rows `32 c .. 32 c + 31` at lane `m % 32`; each 32-bit word has four byte sub-columns `[0:7] [8:15] [16:23] [24:31]` and `SFA_ID` (0-3, the descriptor bits 29-30) picks which byte is the scale (the four IDs are the four coloured byte sub-columns), so a word carries four instructions' worth of scales for the same row. `scale_B` (Figure 257): eight columns `X .. X+7`, column `X + c` holds `N` index `32 c .. 32 c + 31` at lane `n % 32`, with the same four byte sub-columns selected by `SFB_ID` (bits 4-5); because B's scale is "duplicated to all 32 lane partitions", the figure's 32 lanes are one partition's copy. The 128-lane A form (Figure 238, `sm_107f`+) was not read.

**Second method, CUTLASS `mma_traits_sm100_frag.hpp` `tmem_sf_frg` (lines 437-497, same commit, facts only):** "StorageType is the same as ValueType, i.e., we always use a compact allocation" (so the E8M0 scale is one byte), atom for SFA (and for SFB with `ScaleFactorDuplicated4by1`) `<<<32, MMA_MN/32>, 4>, <VecSize, NSF>> : <<<1, 512>, 32>, <0, 128>>` in the *virtual* address (lane stride 1, one byte-column = 128): `mn % 32` is the lane, `mn / 32` steps **512 virtual = one 32-bit column** (four byte-columns), the `4`-way replication steps 32 lanes ("Data is always replicated across subpartitions"), the `VecSize` elements of one scale share a scale (stride 0) and the `NSF` scales step **one byte** (128). **That is Figure 237/257 as read: the two sources agree** for the 4x1 case (column `X + mn/32`, lane `mn % 32`, scale index = byte sub-column; replicated over the four 32-lane subpartitions). `ScaleFactorDuplicated2by2` (SFB, `N_SM == 2`) has its own atom `<<<32, MMA_MN/2/32>, 2, 2>, ..>` and was not matched to a figure.

**What is missing (the real blockers):** (1) the scales are written into tensor memory by `tcgen05.cp` (shared to tensor memory) or `tcgen05.st`, and **neither statement exists in the IR** (only `Tcgen05Ld`); (2) the scale layout has a second method now, above, for the 4x1 (non-`::2`) case; the 128-lane form and the `::2` SFB 2x2 form are not checked against the figures; (3) `scale_vec::2X/4X` and `block16` belong to `mxf4`/`mxf4nvf4` and wait on 501 and on FP4. **`tcgen05.cp` (PTX 9.7.18.9.2, pages 756-758, text read once):** `tcgen05.cp.cta_group::N.shape{.multicast}{.dst_fmt.src_fmt} [taddr], s-desc;` is an *asynchronous* copy from shared memory (the source is a matrix descriptor, so it reuses `OperandLayout`) into tensor memory; `.shape` one of `128x256b, 4x256b, 128x128b, 64x128b, 32x128b` (the last two require a `.multicast` of `warpx2::02_13`/`::01_23` or `warpx4`); `.dst_fmt.src_fmt` `.b8x16` with `.b6x16_p32` or `.b4x16_p64` decompress 6/4-bit data to 8-bit containers on the way; "All tcgen05 instructions within a kernel must specify the same value for the `.cta_group`"; `sm_100a`+. A `Stmt::Tcgen05Cp { shape, dst: (Tensor alloc, col), src: Place, layout }` would need the **"Data Movement Shape" section (what lands in which lane for each shape), which is unread**, plus an ordering rule (a `tcgen05.mma` that reads scales after a `cp` needs `tcgen05.commit`/`wait`, PTX's "tcgen05.cp -> tcgen05.commit" pipeline lines near 32834, unread in detail). **Data Movement Shape (PTX 9.7.18.2.3, page 709, text read):** a shape is a tuple `lane x size`: `lane` rows of tensor memory, `size` bits across the columns; so `.128x128b` = 128 lanes of 128 bits (4 words per lane), `.4x256b` = 4 lanes of 256 bits, `.128x256b` = 128 lanes of 256 bits. **Which source bytes land in which lane/word for `.cp` is not stated in that section's text** (the fragment figures 186-190 are for `.ld`/`.st` only), so the placement rule is unread. **Next read:** where PTX gives the shared-memory source order for `.cp` (the matrix-descriptor sections 9.7.18.3-5) and the `cp` ordering lines; then this row is buildable for `128x128b`/`4x256b` at one `cta_group`.

## 5i. Negate, f16 `D`, and sub-byte operands (2026-11-25; negate and `D` two methods, packing one method, sub-byte not built)

**Built** (`lane/u8c-tcgen05-f16d`): `negate_a`/`negate_b` and `acc = F16`. Instruction descriptor (PTX ISA 9.5 Tables 52-54): bit 13 negate A, bit 14 negate B, `dtype` bits 4-5 with `F16 = 0` for `.kind::f16` and `.kind::f8f6f4` (`F32 = 1`); 9.7.18.10.1 Table 64 says negate is supported for `.kind::tf32`, `.kind::f16`, `.kind::f8f6f4` (and `mxf8f6f4`, `mxf4`, `mxf4nvf4`), not `.kind::i8`. CUTLASS `mma_sm100_desc.hpp` `InstrDescriptor` agrees field for field (`c_format_` bits 4-6 `0 = F16`; `a_negate_`/`b_negate_` bits 13/14 "valid only for F32F16Format and MXF8F6F4Format"). Different methods (PTX tables read as text, CUTLASS header), so the two agree independently. `D` in tensor memory (9.7.18.10.4.1): "sub-word elements of matrix D are expected not to be packed within a 32-bit Tensor Memory word ... a single 16-bit element in its lower 16 bits": one element per word, so the oracle's tensor allocation is `U32` words and the binary16 sits in the low half. **Unspecified by PTX, so not claimed:** the upper 16 bits (the oracle writes zero and a kernel must not read them) and how an `F16` accumulate rounds inside the instruction (the oracle rounds once from the exact sum; this is a contract, not a hardware measurement).

**Sub-byte operands (FP6 `E2M3`/`E3M2`, FP4 `E2M1`) read, not built.** PTX 9.7.18.10.4 (figures 202-210 read as images): the only statement of the *shared-memory* packing is for **`.kind::mxf8f6f4`** (9.7.18.10.4.4): elements packed contiguously, with padding "after 16 elements" when dense K is 32 (Figure 207: 16 FP4 = 64 bits then 64 bits of padding; Figure 208: 16 FP6 = 96 bits then 32 bits of padding), none when K is 64 (Figure 209). In tensor memory (A only, 9.7.18.10.4.3) containers are 8-bit, four per 32-bit word (Table 68: FP4 K=32 in 8 bits; FP6 K=64 in 6 bits or K=32... in 8 bits with 2 bits padding); `mxf4`/`mxf4nvf4` pack two FP4 per byte (Figures 210). **Unscaled `.kind::f8f6f4`: PTX silent, CUTLASS-only (single source, and the 5i text before 2026-11-26 got this wrong).** PTX states the shared-memory packing only for `.kind::mxf8f6f4` (above); for the unscaled `.kind::f8f6f4` it says nothing. CUTLASS (`include/cutlass/float_subbyte.h`, BSD-3, facts only; `mma_sm100_desc.hpp` lines 204-206 and 402-411; `mma_traits_sm100.hpp` `SM100_MMA_F8F6F4_SS` line 2472) types the operand with `float_e2m1_unpacksmem_t` (`sizeof_bits` 4, line 145), `float_e2m3_unpacksmem_t` and `float_e3m2_unpacksmem_t` (`sizeof_bits` 6, lines 253, 360), "used to select correct MMA type and TMA type" (lines 108, 215), and these same tags select `MXF8F6F4Format` in the instruction-descriptor builder that `F8F6F4_SS` and `MXF8F6F4_SS` both use; the 8-bit-container types `float_e2m3_unpack8bits_t`/`float_e3m2_unpack8bits_t` (`sizeof_bits` 8, lines 372-379) are named "the register type used in kernel" (`get_unpacked_element_type`, line 389). So CUTLASS says the shared-memory element is 4 or 6 bits wide, i.e. packed, **not** one element per byte (an earlier version of this note said the opposite; that was wrong). It does **not** state the 16-element grouping or the padding, so for the unscaled kind the padding rule is "the mxf8f6f4 rule applies" by inference from the shared type tags, not a statement by either source: not built on that inference.

**Why FP6/FP4 `Tcgen05Mma` tiles are not built (named blockers, 2026-11-26):** (1) the tile is bit-addressed (FP6: 16 elements = 12 bytes + 4 padding; the oracle's `Shared` cell is one element) and (2) the 2026-11-05 U9b ruling makes sub-byte buffers read-only in kernels (`kernel_check.rs` 679: no `Store` of a sub-byte element), so a kernel cannot fill such a tile except by a byte-wise bulk copy of packed data (the TMA-shaped path) that the IR does not have for sub-byte. The `Cast` endpoints exist (0.31.7). Next, when someone picks it up: a bulk byte copy into a byte `Shared` allocation plus a `Tcgen05Mma` that reads the PTX 16-element-plus-padding format from bytes; that needs a ruling on whether the unscaled kind may use the inferred padding.

## 5j. Design: the tile-fill op for bit-addressed FP6/FP4 tiles (2026-11-26, PM ruling A; design only, not built)

**Ruling (pm-kernels 2026-11-26):** the unscaled `.kind::f8f6f4` uses the `mxf8f6f4` shared-memory padding **by inference** ("inferred, CUTLASS-shared tags, PTX silent"); a device or `ptxas` check is added later if one exists. A tile-fill op **distinct from a sub-byte `Store`** keeps U9b (sub-byte buffers read-only in kernels) intact.

**The op.** `Stmt::CopyUnpack { dst, src, groups, fmt, bar }`: one thread copies `groups` groups of 16 elements from the packed global sub-byte buffer place `src` (a readable buffer of `F4E2M1` or `F6E2M3`/`F6E3M2`, packed as KISS packs it: FP4 two per byte, low nibble = even index (`oracle/elem.rs`, KISS-CLASSIFY 6.1); FP6 is not pinned by KISS for buffers, so FP6 sources wait on that pin) into the **byte** `Shared` allocation place `dst` (a `U8` allocation), **one 16-byte slot per group**: `F4`: the 8 data bytes, then 8 bytes of padding; `F6`: the 12 data bytes, then 4 bytes of padding (PTX Figures 207 and 208: "16 elements ... with 64-bit / 32-bit padding at the end"). It completes on `bar` like `CopyBulk` (`complete_tx` of `groups * 16` bytes) and a consumer needs the same acquire. It is not a `Store` of a sub-byte element (it moves whole bytes), so U9b is unchanged: **no `[ASK]` is needed for U9b.** The hardware analogue is a tensor-map copy whose data type unpacks 16 sub-byte elements into a 16-byte slot (`.b4x16_p64`, `.b6x16_p32` appear in `tcgen05.cp`'s `.dst_fmt.src_fmt`); the oracle models the effect, not the tensor map. The pad bytes are written zero by the oracle and are **unspecified** by PTX (a kernel must not read them).

**What reads it.** `Tcgen05Mma` with `ab`/`b_ty` an MX element reads its A and B tiles from a `U8` `Shared` allocation: row `r` is `K = 32` elements = **two 16-byte slots** (so 32 bytes per row, RowMajor and oracle-only exactly as the 8-bit slice 1), element `k` is slot `k / 16`, element `k % 16` of it; FP4: nibble `k % 16 % 2` of byte `(k % 16) / 2` (KISS low-nibble-first); FP6: bits `[6e, 6e + 6)` of the slot, **LSB-first, an assumption**: the figure (208) shows 16 consecutive 6-bit cells and does not say whether the stream is read from the low or the high bit. **Tags for the code and this note:** FP4 nibble order = KISS-pinned (buffers) and assumed to carry to the smem slot; FP6 bit order = assumed; unscaled-kind padding = "inferred, CUTLASS-shared tags, PTX silent"; K = 32 only (K = 64 has no padding and is `mxf8f6f4`, which needs the scales).

**Second source for the slot and the bit order (added 2026-11-26, PTX section 5.5.1.1, Figures 5-7 read as images; a different section and method from 9.7.18.10.4).** The tensor-copy types name the slot: `.b4x16_p64` = "sixteen contiguous 4-bits of data ... copied from global memory to the shared memory with the append of 64-bits of padding" (Figure 5: an 8-byte global group becomes 8 data bytes then 8 padding bytes), `.b6x16_p32` = sixteen 6-bit elements with "32-bits of padding" (Figure 6: 12 B then 4 B), and "the padded region that gets added is un-initialized" (so the oracle's zero pad is its own choice). The sub-byte types are "packed contiguously in the global memory"; the figures label the global group LSB at the left and MSB at the right with the elements running left to right, so **element 0 is the lowest bits: FP4 low nibble first, FP6 LSB-first** (figure read, not stated in words). That closes the nibble-order assumption (and the FP6 bit-order one) with PTX itself, independently of the KISS buffer packing, and it is kind-independent (the copy type names no MMA kind), which supports the inferred padding for the unscaled `.kind::f8f6f4`; PTX still does not say which kind consumes which slot format, so the "inferred" tag on the unscaled kind stays.

**Slices.** (a) `CopyUnpack` for FP4 (checker: `dst` is a `U8` `Shared` place, `src` an F4 global buffer, `groups * 8` source bytes in range; oracle: slots; trap on a missing acquire; cpu-c declines like `CopyBulk`); (b) `Tcgen05Mma` reads FP4 tiles from the slots (RowMajor), mixed with FP8 on the other operand (the type fields are independent); (c) FP6 once the buffer packing is pinned; (d) canonical/swizzled layouts of these tiles, which also wait on a second source for how a 16-byte slot sits in a core matrix. The patent note on `CopyBulk` (US11803380B2) applies to this op as well: emitters for other manufacturers decline it.

**`tcgen05.cp` ordering read (2026-11-26, PTX text, 9.7.18.6.x pipelined-instruction list, lines near PTX page 737; one method).** Instructions of the same pipeline order without a wait: `tcgen05.cp.<not .4x256b>.cta_group::N` (writes) then `tcgen05.mma.cta_group::N` (A and metadata reads) at the same N and address; `.4x256b` likewise at the same N; `tcgen05.mma` A/metadata reads before a later `tcgen05.cp` writes; `tcgen05.shift` before `tcgen05.mma`. So a `cp` that fills the scale matrices needs no explicit commit/wait before an `mma` that reads them (same `cta_group`, same address): the IR statement may be ordered by program order, which is simpler than `CopyBulk`'s barrier. **Still unread (named blocker for building `Tcgen05Cp`):** which source bytes land in which tensor-memory lane and word for each shape (not in the shape section, 9.7.18.2.3; figures 186-190 are `ld`/`st` only) and the shared-memory matrix-descriptor read order for `cp`. Without that the scale layout (5h, columns `X + mn/32`, lane `mn % 32`) can be modelled only as "the scales are in tensor memory", i.e. a `Tcgen05St` of the scale words, which is also unbuilt; board 501 is not the blocker for the UE8M0 `mxf8f6f4` case, the placement rule is.

**E2M1's descriptor code depends on the kind (KISS finding 2026-11-26, PTX Tables 52-53 and CUTLASS; checked against our notes).** `.kind::f8f6f4` (Table 52, and 54 for `mxf8f6f4`): `E4M3 = 0, E5M2 = 1, E2M3 = 3, E3M2 = 4, E2M1 = 5`; `.kind::mxf4`/`mxf4nvf4` (Table 53): `E2M1 = 1`, scale `UE4M3 = 0, UE8M0 = 1` (CUTLASS `ScaleFormat`; PTX also lists `UE5M3 = 2`, which CUTLASS lacks; UE4M3/UE5M3 stay board 501). CUTLASS `mma_sm100_desc.hpp` agrees: `MXF8F6F4Format::E2M1 = 5` and `MXF4Format::E2M1 = 1`. **What this means for our IR:** `Tcgen05Mma` carries no descriptor code and no kind field; an `F4E2M1` operand on it is **`.kind::f8f6f4` only (code 5)**, the sole kind built. The `mxf4`/`mxf4nvf4` kinds (code 1, packed two-per-byte operands, scale vectors) are a different statement shape and are not built; when they are, the kind must be explicit in the statement (or a distinct statement), never inferred from `ab = F4E2M1`, because the same `ElementKind` maps to two codes. Test status: the IR has no code to test (the emitter derives it), so the guard is that the checker admits `F4E2M1` only on this kind-less `f8f6f4` statement; the per-kind code test belongs with the first emitter or the `mxf4` statement.
